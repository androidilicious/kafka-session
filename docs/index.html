Kafka Lab Walkthrough

It is Black Friday and your online store is about to crash. This page starts with that story, then takes you through eleven hands-on steps. Each step asks one question, answers it with one Kafka idea, and gives you a command to run.

    00

    Black Friday at Bull City Market

    You run the checkout for an online store. When a customer places an order, four other things have to happen: a confirmation email goes out, stock is reduced, the order is checked for fraud, and the live sales board is updated.

    The store was first built the simplest way: checkout calls each service, one after another, and waits for each one to answer. The picture below calls this design Direct calls. On a normal Tuesday it works. Then Black Friday starts.

    Design
    Each dot is one order, labelled with its customer number.

    Try this. In Direct calls, press Take inventory down and watch the checkout counter. Bring it back. Then switch to With Kafka and do the same thing.

    • Direct calls: one broken service stops every order. Customers see a loading screen, and orders placed while it is broken can be lost. This is called tight coupling: each service only works if the others are working.
    • With Kafka: checkout writes the order down in one shared place and moves on. Each service reads from that place at its own speed. A broken service falls behind, then catches up.
    01

    Put Kafka in the middle

    What is the thing in the middle, and where does it run?

    The thing in the middle is a Kafka server, called a broker. It saves every order it receives and hands them to any service that asks. In this lab the broker runs in Docker on your laptop. So does Kafka UI, a web page that lets you look inside the broker. Your Python scripts run on your laptop and connect to the broker at localhost:9092.

    You need Docker Desktop running and Python 3.10 or newer.

    The page uses three kinds of box. Only type what is in a Run box.

    • Run (bright edge and a filled tag): a command to type in the terminal named in its title.
    • Code, do not run (outlined box): a few lines from one of the scripts, to read.
    • Output (dim text): what your terminal should print.

    ZooKeeper used to keep track of which brokers were running. Newer Kafka versions do that job themselves. This is called KRaft mode. That is why docker-compose.yml has one Kafka container and no ZooKeeper.

    02

    Checkout produces events

    How does checkout hand over an order without calling anyone?

    It writes an event: a small record that says "this happened". An event has a key (here the customer id), a value (the order as JSON) and a timestamp. A program that writes events is a producer. It does not know who will read them, and it does not wait for anyone to read them.

    producer.py plays the checkout service and places one fake order per second.

    This is the part of producer.py that sends an order to Kafka:

    Code, do not runproducer.py (the key lines)
    # Settings come from the .env file
BOOTSTRAP = os.getenv("KAFKA_BOOTSTRAP_SERVERS", "localhost:9092")  # the broker's address
TOPIC = os.getenv("KAFKA_TOPIC", "orders")                          # the topic name

producer = Producer({"bootstrap.servers": BOOTSTRAP})  # connect to the broker

producer.produce(
    TOPIC,                      # which topic to write to: orders
    key=order["customer_id"],   # the key decides the partition
    value=json.dumps(order),    # the order itself, as JSON text
    on_delivery=on_delivery,    # Kafka reports back the partition and offset
)
producer.poll(0)                # lets that report come back

    BOOTSTRAP is the address of the broker, localhost:9092. Kafka calls it the bootstrap server because it is the first broker a program contacts. That broker then tells the program about the rest of the cluster.

    That is all a producer does: connect, then call produce with a topic, a key and a value. Now run it:

    RunTerminal A
    python producer.py
    OutputYou should see
    Producing to topic 'orders' on localhost:9092 at 1.0/s. Ctrl+C to stop.
sent  partition=0  offset=0      CUST-1003    815.20  home         Robot Vacuum
sent  partition=1  offset=0      CUST-1034    846.02  electronics  Laptop
sent  partition=0  offset=1      CUST-1001     59.99  toys         Board Game

    Each line shows where Kafka stored the order. The offset is the order's position in its partition, counting from 0. Each partition counts on its own, so the first order in partition 0 and the first order in partition 1 both get offset 0. The next order in partition 0 gets offset 1. Step 08 explains partitions.

    Leave it running. In Kafka UI, open Topics → orders → Messages and click one message to see its key, value, partition and offset.

    Check: no other service is running yet. Where are the orders going?

    Into Kafka, on the broker's disk. Kafka stores events even when nobody is reading them. Checkout is working with no other service running. In the direct-call design that was impossible.

    03

    Topics: one per kind of event

    Do orders, alerts and everything else land in one big pile?

    No. Events are grouped into named topics, one per kind of event. You choose the topics when you design the system, much like you choose the tables for a database.

    This lab uses two, created for you when Kafka started: orders and fraud-alerts. Kafka UI also lists a third, fraud-reviews, which this walkthrough does not use. Look at one:

    RunTerminal B (macOS)
    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --describe --topic orders --bootstrap-server localhost:9092
    RunTerminal B (Windows)
    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --describe --topic orders --bootstrap-server localhost:9092
    OutputYou should see
    Topic: orders   PartitionCount: 3   ReplicationFactor: 1
    Topic: orders   Partition: 0   Leader: 1   Replicas: 1   Isr: 1
    Topic: orders   Partition: 1   Leader: 1   Replicas: 1   Isr: 1
    Topic: orders   Partition: 2   Leader: 1   Replicas: 1   Isr: 1

    The topic is split into three partitions. Step 08 explains why. For now, notice that every line the producer prints has a partition number. You can ignore Leader, Replicas and Isr. They say which broker holds each partition, and we have only one broker.

    Check: ReplicationFactor is 1, which means Kafka keeps one copy of the data. What would a real store use, and why?

    Usually 3. Every partition is then stored on three brokers, so no orders are lost if one broker fails. We have one broker, so there is nowhere to put a second copy.

    04

    Services consume

    Who reads the orders, and how do they know there is a new one?

    A program that reads a topic is a consumer. It subscribes to the topic and keeps asking the broker for anything new. Every consumer has a group id, which is the name of the service it belongs to.

    consumer.py plays a service that reacts to orders. A real service would send the email. Ours only prints each order. Its default group is notifications.

    This is the part of consumer.py that reads orders from Kafka:

    Code, do not runconsumer.py (the key lines, shortened)
    consumer = Consumer({
    "bootstrap.servers": BOOTSTRAP,    # connect to the broker
    "group.id": args.group,            # the service's name: notifications
    "auto.offset.reset": "earliest",   # a new group starts from the oldest order
})
consumer.subscribe([TOPIC])            # which topic to read: orders

while True:
    msg = consumer.poll(1.0)           # ask the broker for the next event
    if msg is None:
        continue                       # nothing new yet, so ask again
    order = json.loads(msg.value())    # turn the JSON text back into an order
    print(msg.partition(), msg.offset(), order["customer_id"])

    A consumer is a loop: connect with a group id, subscribe to a topic, then keep calling poll. Now run it:

    RunTerminal B
    python consumer.py
    OutputYou should see
    Group 'notifications' reading topic 'orders' on localhost:9092. Ctrl+C to stop.
got   partition=1  offset=0      CUST-1034    846.02  electronics  Laptop, Chapel Hill
got   partition=0  offset=0      CUST-1003    815.20  home         Robot Vacuum, Chapel Hill

    First it prints the orders that were placed before it started. After that it prints each new order as soon as Terminal A sends it.

    Check: the first lines jump between partitions. Is the consumer reading out of order?

    No. Each partition is read in order: offset 0, then 1, then 2. Kafka only promises order inside one partition, not between partitions.

    05

    Every service gets every order

    Inventory needs the same orders. Does it have to share with notifications?

    No. Each consumer group gets every event and keeps its own bookmark. The bookmark is the offset the group has read up to, and Kafka calls it the committed offset. To add a new service, you change nothing in checkout or in any other service.

    Leave A and B running. Start the inventory service:

    RunTerminal C
    python consumer.py --group inventory

    This is the same script as Terminal B. The only difference is one setting: "group.id" is now inventory, so Kafka treats it as a separate service.

    Terminal C prints every order too, including those placed before it existed.

    Check: in Kafka UI, open Consumers. How many groups are there, and what is each one's lag (the number of orders it has not read yet)?

    Two: notifications and inventory. Both show a lag of 0 or a few orders. Lag is rarely exactly 0 because a consumer saves its bookmark every 5 seconds, not after every order.

    06

    Inventory goes down

    This is the outage from the story. What happens to the orders now?

    They wait in the topic. The number of orders a group has not read yet is its lag. Kafka works it out for each partition: the newest offset minus the group's bookmark. Teams that run real systems watch lag to see whether a service is keeping up.

    Stop Terminal C (inventory) with Ctrl+C. Leave checkout running for 30 seconds, then run:

    RunTerminal C (macOS)
    docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --describe --group inventory --bootstrap-server localhost:9092
    RunTerminal C (Windows)
    docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --describe --group inventory --bootstrap-server localhost:9092
    OutputYou should see something like
    Consumer group 'inventory' has no active members.
GROUP      TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
inventory  orders  0          11              25              14
inventory  orders  1          12              17              5
inventory  orders  2          3               10              7

    CURRENT-OFFSET is the group's bookmark. LOG-END-OFFSET is where the next order will be written. LAG is the difference between them.

    The same numbers are in Kafka UI under Consumers → inventory. Look at Terminals A and B: checkout and notifications never noticed. Now bring inventory back:

    RunTerminal C
    python consumer.py --group inventory

    It prints all the orders it missed at once, then goes back to one order per second.

    Check: were any orders lost or handled twice?

    No. Inventory started again from its bookmark in each partition, so it skipped nothing and repeated nothing. Compare that with the direct-call design, where the same outage froze checkout.

    07

    Kafka keeps the orders

    Once every service has read an order, is it gone?

    No. Many older messaging systems delete a message once it is delivered. Kafka keeps every event for a set time, called the retention time (7 days by default). So a service can start late, stop and come back, or read everything again.

    Say the analytics team wants to study the whole day. Use a group name Kafka has never seen:

    RunTerminal D
    python consumer.py --group replay-1

    Every order since the topic was created prints again, starting at offset 0. Stop it with Ctrl+C when it catches up.

    Check: why did replay-1 start at offset 0 while inventory resumed where it left off?

    inventory has a bookmark, so it carries on from there. replay-1 is new and has no bookmark. A consumer with no bookmark uses its auto.offset.reset setting to decide where to start. consumer.py sets it to earliest, which means the start of the topic.

    Check: if Kafka stores everything, is it a database?

    No. You cannot ask Kafka "what is in stock right now?" or look up one customer. A database holds how things are now. Kafka holds the list of everything that happened. Real systems use both.

    08

    Partitions: more checkout lanes

    On Black Friday, one list of orders cannot be written and read fast enough. Now what?

    Split it up, the way a store opens more checkout lanes. A topic is split into partitions. Each partition is its own list, and an event's position in that list is its offset. Kafka uses the event's key to choose the partition: it turns the key into a number (this is called hashing), and the number picks the partition. The same key always gives the same number, so one customer's orders always go to the same partition. Kafka keeps events in order inside a partition, so that customer's orders stay in order.

    Try it here first. Send orders from different customers and watch where they land. Then stop a group and send more.

    Now on the real thing. Stop the producer in Terminal A with Ctrl+C and start it again at 5 orders per second. At that speed the same customers show up more often. Leave it at this speed for the rest of the lab.

    RunTerminal A
    python producer.py --rate 5

    Pick one customer id and follow it for 20 seconds. For example, CUST-1004 lands on partition 1 every time.

    Check: does a customer's partition ever change? What would break if it did?

    No, as long as the topic has 3 partitions. The rule is: turn the key into a number, divide it by 3, and the remainder (0, 1 or 2) is the partition. If the partition changed, one customer's orders could be read in the wrong order, and a fraud rule like "4 orders in 2 seconds" could miss them.

    09

    Add helpers to a busy service

    Orders now arrive on three lanes at once. How does one inventory service keep up?

    Start more copies of it with the same group id. Kafka gives each partition to exactly one consumer in the group, so the copies share the work and no order is handled twice. When a copy joins or leaves, Kafka hands out the partitions again. That is called a rebalance.

    Terminal C is still running inventory. Stop Terminals B and D, then start a second inventory worker in Terminal B:

    RunTerminal B
    python consumer.py --group inventory

    Look at the partition= column in Terminals B and C. One prints two of the partitions and the other prints the third. Now stop one of them with Ctrl+C. Within a few seconds, the one still running prints all three.

    Check: the topic has 3 partitions. What happens if you start a fourth inventory worker?

    It gets no partition and has nothing to do. A group can have at most one working consumer per partition, so 3 partitions means at most 3 workers.

    10

    Chain reactions: fraud alerts and a live sales board

    What if one event should set off another event?

    A program can be a consumer and a producer at the same time. It reads from one topic, does some work, and writes to another topic. Link a few of these together and you have a pipeline. A consumer can also keep totals as events arrive, which is how live dashboards work.

    producer.py ──> [orders] ──> fraud_detector.py ──> [fraud-alerts]
                    │                                    │
                    └────────> dashboard.py <────────────┘

    Stop the inventory workers. Keep the producer running at 5 orders per second.

    RunTerminal B
    python fraud_detector.py

    The part of fraud_detector.py that matters. It is the consumer loop from step 04 with a produce call from step 02 at the end:

    Code, do not runfraud_detector.py (the key lines)
    consumer.subscribe([TOPIC])            # read from: orders

while True:
    msg = consumer.poll(1.0)           # consume: get the next order
    if msg is None:
        continue
    order = json.loads(msg.value())

    reasons = check(order)             # process: apply the two fraud rules
    if not reasons:
        continue                       # a normal order, so nothing to write

    alert = {"reasons": reasons, "order": order}
    producer.produce(                  # produce: write the alert
        ALERTS_TOPIC,                  # to a second topic: fraud-alerts
        key=order["customer_id"],      # same key, so the alert follows the customer
        value=json.dumps(alert),
    )

    The part of dashboard.py that matters. It reads two topics and adds things up as events arrive:

    Code, do not rundashboard.py (the key lines)
    consumer = Consumer({
    "bootstrap.servers": BOOTSTRAP,
    "group.id": "dashboard",
    "auto.offset.reset": "earliest",       # start from the oldest event
    "enable.auto.commit": False,           # never save a bookmark
})
consumer.subscribe([TOPIC, ALERTS_TOPIC])  # one consumer, two topics

while True:
    msg = consumer.poll(1.0)
    if msg is None or msg.error():
        continue
    data = json.loads(msg.value())
    if msg.topic() == ALERTS_TOPIC:        # which topic did this event come from?
        alerts.update(data["reasons"])     # an alert: count it by reason
    else:
        count += 1                         # an order: count it
        total += data["amount"]            # and add it to the revenue

    The detector has two rules: one order of 3000 or more, or 4 orders from one customer within 2 seconds. In Kafka UI, open the fraud-alerts topic and read a message.

    Check: the detector remembers each customer's recent orders. If you ran two detectors in the same group, could one customer's orders be split between them?

    No. The key sends a customer to one partition (step 08), and a partition belongs to one consumer in the group (step 09). So each customer is seen by exactly one detector.

    Check: stop and restart dashboard.py. Its totals come back. From where?

    From Kafka. The dashboard never saves a bookmark, so every time it starts it reads both topics from the beginning and adds everything up again (step 07). The orders in Kafka are the real record. The totals are worked out from them.

    The questions you answered

    QuestionKafka's answer
    How do services stop depending on each other?A broker in the middle stores events
    Who writes, and who reads?Producers write, consumers read, and neither knows the other
    How are events organized?Into topics, one per kind of event
    How do several services read the same events?Each consumer group keeps its own bookmark, the committed offset
    What happens when a service is down?Its lag grows, then it catches up
    Are events deleted after reading?No, they stay for the retention time and can be replayed
    How does it handle Black Friday volume?Partitions, with the key keeping each customer in order
    How does one service go faster?Add consumers to the same group. Kafka shares out the partitions (a rebalance)
    How do events trigger more events?A program reads one topic and writes to another (consume, process, produce)
