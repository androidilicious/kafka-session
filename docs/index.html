    Black Friday at Bull City Market

    You run the checkout for an online store. When a customer places an order, three other things have to happen: a confirmation email goes out, stock is reduced, and the order is checked for fraud.

    The store was first built the simplest way: checkout calls each service, one after another, and waits for each one to answer. The picture below calls this design Direct calls. On a normal Tuesday it works. Then Black Friday starts.

    Design
    Each dot is one order, labelled with its customer number.

    Try this. In Direct calls, press Take inventory down and watch the checkout counter. Bring it back. Then switch to With Kafka and do the same thing.

    • Direct calls: one broken service stops every order. Customers see a loading screen, and orders placed while it is broken can be lost. This is called tight coupling: each service only works if the others are working.
    • With Kafka: checkout writes the order down in one shared place and moves on. Each service reads from that place at its own speed. A broken service falls behind, then catches up.
    01

    Put Kafka in the middle

    What is the thing in the middle, and where does it run?

    The thing in the middle is a Kafka server, called a broker. It saves every order it receives and hands them to any service that asks. In this lab the broker runs in Docker on your laptop. So does Kafka UI, a web page that lets you look inside the broker. Your Python scripts run on your laptop and connect to the broker at localhost:9092.

    You need Docker Desktop running and Python 3.10 to 3.14. Python 3.15 is too new: the Kafka library does not install on it yet.

    02

    Checkout sends orders

    How does checkout hand over an order without calling anyone?

    It writes an event: a small record that says "this happened". An event has a key (here the customer id) and a value (the order as JSON). A program that writes events is a producer. Events go into a named topic, and ours is called orders. The producer does not know who will read the events, and it does not wait for anyone to read them.

    producer.py plays the checkout service and places one fake order per second. This is the part of it that sends an order to Kafka:

    Code, do not runproducer.py (the key lines)
    # Settings come from the .env file
BOOTSTRAP = os.getenv("KAFKA_BOOTSTRAP_SERVERS", "localhost:9092")  # the broker's address
TOPIC = os.getenv("KAFKA_TOPIC", "orders")                          # the topic name

producer = Producer({"bootstrap.servers": BOOTSTRAP})  # connect to the broker

producer.produce(
    TOPIC,                      # which topic to write to: orders
    key=order["customer_id"],   # the key decides the partition
    value=json.dumps(order),    # the order itself, as JSON text
    on_delivery=on_delivery,    # Kafka reports back the partition and offset
)
producer.poll(0)                # lets that report come back

    BOOTSTRAP is the address of the broker, localhost:9092. That is all a producer does: connect, then call produce with a topic, a key and a value. Now run it:

    RunTerminal A
    python producer.py
    OutputYou should see
    Producing to topic 'orders' on localhost:9092 at 1.0/s. Ctrl+C to stop.
sent  partition=0  offset=0      CUST-1003    815.20  home         Robot Vacuum
sent  partition=1  offset=0      CUST-1034    846.02  electronics  Laptop
sent  partition=0  offset=1      CUST-1001     59.99  toys         Board Game

    Each line shows where Kafka stored the order:

    • partition: the orders topic is split into three lists, called partitions, numbered 0, 1 and 2. Kafka uses the key to pick one, and the same customer always goes to the same partition.
    • offset: the order's position in its partition, counting from 0. Each partition counts on its own, so the first order in partition 0 and the first order in partition 1 both get offset 0.

    Leave it running. In Kafka UI, open Topics. The orders row shows 3 partitions and a number of messages that keeps growing. Click orders, then Messages, and click one message to see its key and value.

    Check: no other service is running yet. Where are the orders going?

    Into Kafka, on the broker's disk. Kafka stores events even when nobody is reading them. Checkout is working with no other service running. In the direct-call design that was impossible.

    03

    Two services read the orders

    Who reads the orders, and can two services read the same ones?

    A program that reads a topic is a consumer. It subscribes to the topic and keeps asking the broker for anything new. Every consumer has a group id, which is the name of the service it belongs to. Each consumer group gets every event.

    consumer.py plays a service that reacts to orders. A real service would send the email. Ours only prints each order. This is the part that reads from Kafka:

    Code, do not runconsumer.py (the key lines, shortened)
    consumer = Consumer({
    "bootstrap.servers": BOOTSTRAP,    # connect to the broker
    "group.id": args.group,            # the service's name: notifications
    "auto.offset.reset": "earliest",   # a new group starts from the oldest order
})
consumer.subscribe([TOPIC])            # which topic to read: orders

while True:
    msg = consumer.poll(1.0)           # ask the broker for the next event
    if msg is None:
        continue                       # nothing new yet, so ask again
    order = json.loads(msg.value())    # turn the JSON text back into an order
    print(msg.partition(), msg.offset(), order["customer_id"])

    A consumer is a loop: connect with a group id, subscribe to a topic, then keep calling poll.

    Start the notifications service in a second terminal. With no extra option, the script uses the group id notifications:

    RunTerminal B
    python consumer.py
    OutputYou should see
    Group 'notifications' reading topic 'orders' on localhost:9092. Ctrl+C to stop.
got   partition=1  offset=0      CUST-1034    846.02  electronics  Laptop, Chapel Hill
got   partition=0  offset=0      CUST-1003    815.20  home         Robot Vacuum, Chapel Hill

    First it prints the orders that were placed before it started. After that it prints each new order as soon as Terminal A sends it.

    Now start the inventory service in a third terminal. It is the same script with a different group id, so Kafka treats it as a separate service:

    RunTerminal C
    python consumer.py --group inventory

    Terminal C prints every order too, including those placed before it started. Notifications and inventory do not share the orders or compete for them. To add inventory, you changed nothing in checkout or in notifications.

    In Kafka UI, open Consumers. You should see both groups, each with one member.

    Check: what would happen if you started a second python consumer.py without --group inventory?

    Both programs would be in the notifications group. Kafka would treat them as two copies of one service and split the orders between them, so each would get only part. A different group id is what makes a separate service.

    04

    Inventory goes down and comes back

    This is the outage from the story. What happens to the orders now?

    They wait in the topic. Each group keeps a bookmark that says how far it has read. Kafka calls it the committed offset. The number of orders a group has not read yet is its lag.

    Stop Terminal C (inventory) with Ctrl+C. Leave checkout and notifications running, and wait 30 seconds.

    In Kafka UI, open Consumers. The inventory row shows 0 members, and its Consumer Lag grows each time you refresh the page. Now look at Terminals A and B: checkout and notifications never noticed.

    Bring inventory back:

    RunTerminal C
    python consumer.py --group inventory

    It prints all the orders it missed at once, then goes back to one order per second. In Kafka UI its lag drops back to 0 or close to it. Lag is rarely exactly 0, because a consumer saves its bookmark every 5 seconds, not after every order.

    Check: were any orders lost or handled twice?

    No. Inventory started again from its bookmark, so it skipped nothing and repeated nothing. Compare that with the direct-call design, where the same outage froze checkout.

    Check: once every service has read an order, does Kafka delete it?

    No. Kafka keeps every event for a set time, called the retention time (7 days by default). That is why inventory could come back late and still read everything.

    05

    One event sets off another

    What if one event should set off another event?

    A program can be a consumer and a producer at the same time. It reads from one topic, does some work, and writes to another topic.

    producer.py ──> [orders] ──> fraud_detector.py ──> [fraud-alerts]

    The fraud detector reads every order and writes an alert when one looks suspicious. In Terminal C, stop inventory with Ctrl+C and start the detector:

    RunTerminal C
    python fraud_detector.py

    The part of fraud_detector.py that matters. It is the consumer loop from step 03 with a produce call from step 02 at the end:

    Code, do not runfraud_detector.py (the key lines)
    consumer.subscribe([TOPIC])            # read from: orders

while True:
    msg = consumer.poll(1.0)           # consume: get the next order
    if msg is None:
        continue
    order = json.loads(msg.value())

    reasons = check(order)             # process: apply the two fraud rules
    if not reasons:
        continue                       # a normal order, so nothing to write

    alert = {"reasons": reasons, "order": order}
    producer.produce(                  # produce: write the alert
        ALERTS_TOPIC,                  # to a second topic: fraud-alerts
        key=order["customer_id"],      # same key, so the alert follows the customer
        value=json.dumps(alert),
    )
    OutputTerminal C should show
    Reading 'orders', writing alerts to 'fraud-alerts'. Ctrl+C to stop.
ALERT LARGE_ORDER           CUST-1038   6012.77  Robot Vacuum, New York
ALERT VELOCITY              CUST-1020    688.36  Robot Vacuum, Raleigh

    The detector has two rules: one order of 3000 or more, or 4 orders from one customer within 2 seconds. It first checks every order placed so far, so some alerts appear straight away. After that, suspicious orders are rare, and a new alert can take a minute to appear.

    In Kafka UI, open Topics, click fraud-alerts, then Messages, and click one message. Checkout did not write it. The detector did.

    Check: what had to change in checkout to add the fraud detector?

    Nothing. The detector only needed the name of the topic to read. That is the fix for the tight coupling in the story.

    The questions you answered

    QuestionKafka's answer
    How do services stop depending on each other?A broker in the middle stores events
    Who writes, and who reads?Producers write, consumers read, and neither knows the other
    Where do events go?Into a topic, which is split into partitions
    How do several services read the same events?Each consumer group gets every event and keeps its own bookmark, the committed offset
    What happens when a service is down?Its lag grows, then it catches up
    Are events deleted after reading?No, they stay for the retention time
    How do events trigger more events?A program reads one topic and writes to another
