Kafka Lab Walkthrough

A simulator to play with, then twelve short steps. Each step introduces one Kafka idea, gives you a command to run, shows what you should see, and ends with a question. You will build a small fraud-detection pipeline on a stream of fake bank transactions.

    The idea in one picture

    Kafka stores messages in a topic. A topic is split into partitions, and each partition is a list that only grows at the end. Every message gets a position number in its partition, called an offset. Readers never remove messages. Each group of readers only remembers how far it has read.

    Live flow

    Each dot is one transaction, labelled with its account. Dots with an orange ring are large amounts.
    • The key picks the lane. Watch one account number: it always travels through the same partition.
    • At the end of the lane each message goes to both groups. Groups do not compete with each other.
    • The fraud detector reads one topic and writes to another. Only the ringed dots become alerts.

    Now drive it yourself, before touching a terminal. Send transactions from different accounts and watch where they land. Then stop a reader group and send more.

    Dashed boxes are messages a stopped group has not read yet.
    • Each account always lands in the same row. That row is its partition.
    • Stopping printer does not stop the producer or the audit group. Its unread messages wait, and the count of them is its lag.
    • Starting it again continues from where it stopped. Nothing is lost and nothing is read twice.

    02

    Topics and partitions

    A topic is a named stream, like a table name. Its partitions are what let Kafka spread a topic across machines and let several readers share the work.

    The lab created three topics for you when it started. Look at one:

    Terminal (macOS)
    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --describe --topic transactions --bootstrap-server localhost:9092
    PowerShell (Windows)
    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --describe --topic transactions --bootstrap-server localhost:9092
    You should see
    Topic: transactions   PartitionCount: 3   ReplicationFactor: 1
    Topic: transactions   Partition: 0   Leader: 1   Replicas: 1   Isr: 1
    Topic: transactions   Partition: 1   Leader: 1   Replicas: 1   Isr: 1
    Topic: transactions   Partition: 2   Leader: 1   Replicas: 1   Isr: 1

    In Kafka UI, open Topics. You should see transactions, fraud-alerts and fraud-reviews, all empty.

    Check: ReplicationFactor is 1. What would a real cluster use, and why?

    Usually 3. Each partition is then copied to three brokers, so the data survives if one broker dies. We have one broker, so there is nowhere to put a second copy.

    03

    Produce messages

    A producer is any program that writes to a topic. It does not know or care who will read the messages. The broker replies to each write with the partition and offset where the message was stored.

    Terminal A
    python producer.py
    You should see
    Producing to topic 'transactions' on localhost:9092 at 1.0/s. Ctrl+C to stop.
sent  partition=0  offset=0      ACC-1013    526.19  branch  Target
sent  partition=1  offset=0      ACC-1030    224.63  atm     Delta
sent  partition=1  offset=1      ACC-1005    433.21  branch  Shell

    Leave it running. In Kafka UI, open Topics → transactions → Messages and look at one message. It has a key (the account id), a value (JSON), a partition and an offset.

    Check: no consumer is running. Where are the messages going?

    Into the topic, on the broker's disk. Kafka stores messages whether or not anyone is reading. That is the main difference from a classic message queue.

    04

    Keys and ordering

    The producer sends each transaction with a key, the account id. Kafka hashes the key to choose the partition, so the same key always goes to the same partition. Order is only guaranteed inside one partition, so this is how one account's transactions stay in order.

    Stop the producer with Ctrl+C and restart it faster, so accounts repeat sooner:

    Terminal A
    python producer.py --rate 5

    Pick one account id and follow it for 20 seconds. For example, ACC-1005 lands on partition 1 every time.

    Check: does an account's partition ever change? What would break if it did?

    It never changes while the topic has 3 partitions, because partition = hash(key) mod 3. If it changed, two transactions from one account could be read in the wrong order, and a fraud rule like "4 transactions in 2 seconds" would miss them.

    Stop it again and go back to the normal speed for the next steps: python producer.py

    05

    Consume messages

    A consumer reads from a topic. Every consumer belongs to a consumer group, and Kafka stores the group's position (its committed offset) for each partition.

    Terminal B
    python consumer.py
    You should see
    Group 'printer' reading topic 'transactions' on localhost:9092. Ctrl+C to stop.
got   partition=2  offset=0      ACC-1021    234.18  atm     Uber, New York
got   partition=1  offset=0      ACC-1030    224.63  atm     Delta, Durham
got   partition=1  offset=1      ACC-1005    433.21  branch  Shell, Atlanta

    It first prints everything sent before it started, then each new transaction within a second of Terminal A sending it.

    Check: the first lines jump between partitions. Is the consumer reading out of order?

    No. Inside each partition the offsets go 0, 1, 2 in order. Across partitions there is no order at all, and Kafka does not promise one.

    06

    A second consumer group

    Groups are independent. Each group gets every message and keeps its own offsets. Adding a new reader needs no change to the producer or to other readers.

    Leave A and B running.

    Terminal C
    python consumer.py --group audit

    Terminal C prints every message too, including those sent before it started.

    Check: in Kafka UI, open Consumers. How many groups are there, and what is each one's lag?

    Two: printer and audit. Both show a lag of 0 or a few messages. It rarely reads exactly 0 because a consumer saves its position every 5 seconds, not after every message.

    07

    Stop a consumer and watch lag

    Lag is how many messages a group has not read yet: the end of the partition minus the group's committed offset. It is the number people watch in production to see whether a consumer is keeping up.

    Stop Terminal B with Ctrl+C. Leave the producer running for 30 seconds, then run:

    Terminal B (macOS)
    docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --describe --group printer --bootstrap-server localhost:9092
    Terminal B (Windows)
    docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --describe --group printer --bootstrap-server localhost:9092
    You should see something like
    Consumer group 'printer' has no active members.
GROUP     TOPIC         PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
printer   transactions  1          7               17              10
printer   transactions  2          8               18              10
printer   transactions  0          12              22              10

    The same numbers are in Kafka UI under Consumers → printer. Now start the consumer again:

    Terminal B
    python consumer.py

    It prints the backlog in a burst, then goes back to one message per second.

    Check: were any messages lost or printed twice?

    No. The group resumed from its committed offset on each partition. The messages waited in the topic the whole time.

    08

    Replay from the beginning

    Reading does not delete. Messages stay until the topic's retention time passes (7 days by default), so a new reader can process the full history.

    Use a group name Kafka has never seen:

    Terminal D
    python consumer.py --group replay-1

    Every message since the topic was created prints again, starting at offset 0. Stop it with Ctrl+C when it catches up.

    Check: why did replay-1 start at offset 0 while printer resumed where it left off?

    printer has committed offsets, so it continues from them. replay-1 has none, so the consumer falls back to its auto.offset.reset setting, which consumer.py sets to earliest.

    09

    Share the work inside one group

    Two consumers with the same group id do not both get every message. Kafka gives each partition to exactly one consumer in the group. When a consumer joins or leaves, Kafka reassigns the partitions. This is called a rebalance, and it is how you scale a reader.

    Stop Terminals B, C and D. Start the same group in two terminals:

    Terminal B, then again in Terminal C
    python consumer.py --group team

    Look at the partition= column in each terminal. One prints two of the partitions and the other prints the third. Now stop one of them with Ctrl+C. Within a few seconds the survivor prints all three.

    Check: the topic has 3 partitions. What happens if you start a fourth consumer in the group?

    It gets no partition and sits idle. The number of partitions is the limit on how many consumers in one group can work at once.

    10

    Build a pipeline

    A program can be a consumer and a producer at once: read from one topic, do some work, write to another. Chaining these is how streaming pipelines are built. Topics are the connections between the stages.

    producer.py ──> [transactions] ──> fraud_detector.py ──> [fraud-alerts]
                      │                                        │
                      └──────────> dashboard.py <──────────────┘

    Stop the extra consumers. Restart the producer faster, then start the detector and the dashboard:

    Terminal A
    python producer.py --rate 5
    Terminal B
    python fraud_detector.py
    Terminal C
    python dashboard.py
    Terminal B should show
    Reading 'transactions', writing alerts to 'fraud-alerts'. Ctrl+C to stop.
ALERT VELOCITY               ACC-1046    611.24  Cosmic Cantina, Atlanta
ALERT LARGE_AMOUNT           ACC-1014   4440.74  Delta, Raleigh

    The detector has two rules: one transaction of 3000 or more, or 4 transactions from one account within 2 seconds. In Kafka UI, open the fraud-alerts topic and read a message.

    Check: the detector keeps each account's recent history in memory. If you ran two detectors in the same group, could one account be split between them?

    No. The key sends an account to one partition (step 04), and a partition belongs to one consumer in the group (step 09). So each account is seen by exactly one detector.

    Check: stop and restart dashboard.py. Its totals come back. From where?

    From Kafka. The dashboard never commits offsets, so on every start it reads both topics from the beginning and rebuilds its totals. The topic is the source of truth, and the totals are just a view of it.

    11

    Add an AI agent (optional)

    An AI agent fits into Kafka like any other program. It is one more consumer group that reads a topic and writes to another.

    Open .env in your editor and set ANTHROPIC_API_KEY to your key. Then:

    Terminal D
    python agent_consumer.py

    For each new alert, the agent asks Claude for a two-sentence review and writes it to fraud-reviews. Open that topic in Kafka UI.

    If the key is blank: the agent starts normally, then stops with an authentication error on the first alert. Never paste your key into a chat or commit .env.
    Check: what had to change in Kafka, the producer or the detector to add the agent?

    Nothing. The agent only needed the name of the topic to read. If you stop it for a minute and restart it, the alerts from that minute are still in the topic and it reviews them then.

    Stop every script with Ctrl+C, then remove the containers and their data:

    What you covered

    • Topic, partition, offset: where messages live and how they are numbered.
    • Producer and key: the key picks the partition, which keeps one account in order.
    • Consumer group and committed offset: each group reads everything at its own pace.
    • Lag and replay: unread messages wait, and old messages can be read again.
    • Rebalance: consumers in one group split the partitions between them.
    • Consume, process, produce: topics connect the stages of a pipeline.
